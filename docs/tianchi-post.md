## 三、为什么做

- **行业现状**：县域种植的批次信息普遍分散在纸笔、聊天记录和个人经验中，缺少统一编号与结构化记录；环境管理依赖人工巡棚；小规模主体难以承担传统溯源的实施成本。
- **具体影响**：收购商核验批次时，无法快速确认接种时间、责任人与异常处理记录；温湿度与 CO₂ 异常往往在造成损失后才被发现；销售环节依赖熟人渠道与电话微信对账，可供库存、价格与订单状态不透明，农户难以判断何时卖、卖给谁。
- **田序的应对**：系统将上述问题拆解为七项可执行能力——
  - 降低录入成本：移动端按农事节点记录，拌料、灭菌、接种、转房、采收各留一条结构化记录，替代纸笔与聊天记录。
  - 缩短查询路径：以批次编号为唯一检索入口，接种时间、责任人、阶段进度与异常处理集中呈现。
  - 提前发现风险：环境数据超过作物阈值后自动生成预警，支持标记处理与手动补录，减少无效巡棚。
  - 降低溯源门槛：批次二维码直达公开溯源页，采购商与消费者无需注册、无需安装即可查看生产记录。
  - 集中产销信息：可供库存、供应信息、采购订单与采购需求在同一模块维护；供应大厅跨账号可见，每条供应都标注对应批次。
  - 完成交易闭环：采购商可在供应大厅直接下单，订单按待付款、待发货、待收货、已完成、已取消流转；取消订单回补库存，本月成交额、待确认订单、可供库存与合作采购商四项指标实时汇总。
  - 降低技术门槛：农技问答默认使用离线规则库，不依赖网络与大模型服务；复杂问题转人工咨询。
- **设计原则**：录入轻、查询快、数据同源、结果可验证。系统不追求功能堆叠，而是保证同一批次的记录在移动端、桌面端与公开页三处口径一致。
- **公开演示**：为便于评审与外部验证，演示环境在浏览器内接管接口请求，所有操作仅作用于当前页面内存，刷新后恢复预置样例。

### 5.1 任务拆解与编码

田序从零搭建，任务拆解与编码是工作量最大的阶段，由 Qoder 在会话内完成需求梳理、领域建模、编码实现、联调与构建修复；我负责确定业务边界与验收标准。

- **交给 Qoder**：从种植业务场景出发完成需求梳理与任务拆解，明确六类角色、核心业务对象、阶段状态流转与页面边界，将工作拆分为数据模型、接口实现、双端页面、演示数据层、扫码溯源与构建发布，并按依赖顺序逐项实现。
- **Qoder 完成的工作**：
  - 领域建模：抽象基地、批次、设备、环境记录、预警、溯源事件、供应、采购需求、订单、农技问答十类核心对象，以批次编号作为主键关联全链路数据。
  - 状态管理：建立育苗、生长、成熟、采收、分级、出售六阶段状态机，阶段推进与农事记录、采收分级联动。
  - 交易闭环：供应信息绑定批次并维护上架、下架日期；采购下单按可供数量校验库存；订单采用 created、paid、shipped、received、cancelled 五态流转，取消订单回补预占库存；成交额、待确认订单、可供库存与合作采购商四项指标由供应与订单数据实时计算。

## 七、技术架构

- **客户端**：Taro 4.2 + React 18 + TypeScript + Sass；一套代码构建 H5 与微信小程序；H5 使用 hash 路由，桌面端启用 DesktopShell，移动端保留 tabBar。
- **服务端**：Express 4 + better-sqlite3；JWT 鉴权 + 六角色 RBAC；REST 风格接口，按角色与资源做权限校验。
- **数据模型**：基地、批次、设备、环境记录、预警、溯源事件、产品、需求、订单、农技问答等表；批次编号为全链路主键。
- **设备接入**：支持 HTTP / MQTT 上报，页面 30 秒刷新，10 分钟无上报判定离线。
- **演示层**：Qoder Sites 静态托管；`demo-fixtures.js` 提供脱敏样例，`demo-mock.js` 在浏览器内接管 `/api/*`，写入仅存于内存。
- **智能问答**：默认离线规则知识库（10 条种植栽培规则，不联网、不产生调用费用）；预留 OpenAI 兼容模型适配层，配置后自动切换，前端无需改动。
- **安全**：验证码一次性有效、登录失败锁定、角色权限后端校验；公开演示不含真实个人信息。

## 八、关键设计取舍

1. **批次作为全链路主键**：基地、环境、溯源、产销与问答均回挂到同一批次编号，避免形成六套互不相干的数据。
2. **双端分工而非等比缩放**：移动端保留底部 tab、单列卡片与全宽按钮，满足现场单手操作；桌面端采用侧栏与高密度表格，满足合作社管理场景。
3. **公开溯源页免登录**：二维码直接打开 `trace.html?code=…`，不加载 App 外壳、不要求注册；公开页的访问成本直接影响溯源能否真正被使用。
4. **设备在线状态以真实上报为准**：静态演示明确标注演示数据，不以伪造的在线状态误导判断；只有真实部署并产生上报时才显示在线。
5. **演示环境与生产环境隔离**：比赛链接为静态托管，数据脱敏、写入仅驻留内存；真实后台独立部署，数据库不直接暴露公网。
